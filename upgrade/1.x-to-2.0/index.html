从 1.x 到 2.0 的升级指南¶

本文档介绍操作员在从 Sōzu 1.1.x 部署升级到 2.0.0 时需要处理的破坏性变更。 2.0.0 是一个主要版本跃迁，因为 1.1.1 之后 main 上的工作在仪表板指标名称、 默认行为和配置加载验证方面积累了破坏性变更。

目标读者¶

在生产中运行 sozu 1.1.x 的操作员，包括：

  • 通过配置管理工具或手工 TOML 管理的小型部署；
  • 多租户部署；
  • 从自有 crate 消费 sozu-command-lib 的嵌入者。

sōzu 升级方式——两条独立路径¶

Sōzu 有两个 Command::new(...).exec() 站点用于重新启动二进制文件， 每个站点有不同的意图。操作员应在运行升级前理解两者。

主进程热升级 —— sozuctl upgrade-main¶

这是操作员触发的路径：

  1. 操作员在运行主进程的 path 安装新二进制（通常在 /usr/bin/sozu）。
  2. 操作员运行 sozuctl --config <cfg> upgrade-main。
  3. 主进程 fork；子进程通过路径重新执行磁盘上的新二进制 （Command::new(executable_path)）。目的是切换版本——基于路径的 exec 是预期行为。
  4. 新主进程通过临时升级 fd 使用 SCM_RIGHTS 继承监听器 fd 和集群状态， 然后向旧主进程发送信号以 soft_stop。旧 worker 排空在途请求并退出。

Worker 自动重启——在主进程内部¶

这是非交互式路径：当 worker panic 或其会话数超过 max_connections 时，主进程会生成替换者。

这里 spawn 必须匹配运行中主进程的版本（否则主进程版本 A 和新 worker 版本 B 会在不同 proto schema 下交换消息并崩溃）。 在 2.0.0 之前，主进程使用了与热升级路径相同的 Command::new(executable_path).exec() 形状——意味着在主进程启动 和 worker 自动重启之间替换磁盘上二进制文件的包升级会无声地 spawn 一个新版本的 worker，与运行中旧版本的主进程竞态。 这是 #515。

2.0.0 的修复在 forked 子进程中立即在 execve(2) 之前打开 /proc/self/exe 并使用 O_PATH，并使用 /proc/self/fd/<n> 用于 worker exec——内核通过魔法符号链接 解析到主进程启动时的原始 inode，无论磁盘替换如何。 forked 子进程继承了主进程的 mmap'd 镜像，因此子进程中的 /proc/self/exe 解析到与主进程启动时相同的原始 inode。 通过自动重启路径生成的 worker 现在在包升级方面无竞态。

热升级路径故意保持不变：在 cp new-sozu /usr/bin/sozu 之后运行 sozuctl upgrade-main 的操作员仍然让新二进制运行新主进程， 与以前完全一样。此分离记录在 bin/src/util.rs::get_executable_exec_path() 的 rustdoc 中。

无法以 O_PATH 打开 /proc/self/exe 时的回退¶

无竞态 worker exec 路径要求 /proc/self/exe 可以以 O_PATH 打开。 在容器（/proc 被屏蔽）、AppArmor / SELinux 配置文件拒绝 r /proc/self/exe 或其他命名空间环境上运行 Sōzu 的操作员 将看到 worker 回退到基于路径的 exec（每次回退在 error! 级别记录）。 在此回退模式下，#515 竞态窗口与 1.1.x 相同。要验证，请在工作器日志 中 grep 字符串 falling back to path-based exec。

无竞态断言¶

在二进制替换下的无竞态由内核测试的 /proc/self/exe 魔法符号链接语义保证； bin/src/util.rs::tests 中的源码内单元测试覆盖辅助函数的形状和 fd 唯一性。

升级前清单（强制）¶

在交换 2.0.0 二进制之前运行这些步骤。没有这些备份， 回滚流程 无法完全恢复 1.1.x 状态。

# 1. 将运行时状态快照为 JSON 备份
sozuctl state save /var/lib/sozu/state.1.1.x.backup.json

# 2. 快照审计日志目录（2.0.0 JSON sink schema 与 1.1.x 消费者不向后兼容）
cp -a /var/log/sozu/audit/ /var/log/sozu/audit.1.1.x.backup/

# 3. 记录运行版本
sozu --version > /var/lib/sozu/version.1.1.x.txt

# 4. 外部快照 Grafana / Prometheus 仪表板——2.0.0 指标重命名会破坏 1.1.x 仪表板。
#    保存 JSON 导出以便需要时回滚。

2.0.0 中的破坏性变更¶

仪表板指标重命名¶

以下指标名称已更改。抓取旧名称的仪表板将变空白直到更新。

1.1.x 2.0.0
client.connections_percentage client.connections_percent
client.max_connections client.connections_max
buffer.number buffer.in_use

高分辨率 client.connections 信号保持不变。来自 SessionManager::incr/decr 的 client.connections_* 每事件发射 已删除——新名称从运行循环中与代理 gauges 一起发射。

操作：更新 Grafana 仪表板、statsd → Prometheus 导出器， 以及引用旧名称的任何 metrics get 脚本。升级前快照现有仪表板 以便回滚时恢复它们。

http.errors 现带有 (cluster_id, backend_id) 标签¶

http.errors 现在使用两个标签发射，并由 metrics.detail 旋钮集中过滤：

  • metrics.detail = "process"（opt-in 落地前的遗留默认值）→ 折叠为代理级计数器（对默认 1.1.x 部署无行为变更）。
  • metrics.detail = "frontend" → 也折叠（无每集群拆分）。
  • metrics.detail = "cluster"（文档默认值）→ 每集群归属。
  • metrics.detail = "backend" → 每集群 + 每后端拆分。

操作：按前端或后端对 http.errors 分组的仪表板现在会看到带标签的发射。 如果 statsd / Prometheus drain 自动将标签剥离到指标名称， 可能会看到新的 http.errors{cluster_id=…,backend_id=…} 系列。 确认 metrics.detail 匹配你的操作员意图。

默认 metrics.detail = "cluster" 抑制每后端 StatsD 系列¶

metrics.detail 是新 TOML 旋钮（配置键 metrics.detail， 默认 "cluster"）在 StatsD 网络 drain 编码它们之前过滤 (cluster_id, backend_id) 标签。默认值匹配每集群聚合级别—— backend_id 在每个指标上被丢弃。

在 1.1.x 中没有此类过滤器：任何以 Some(cluster_id) AND Some(backend_id) 起源的发射—— bytes_in、bytes_out、backend_response_time、 backend_connection_time、每后端 requests——同时到达 network_drain::WriteBuf 的集群聚合和后端细节存储， 因此 StatsD 线携带两个系列：

sozu.cluster.bytes_in,cluster_id=foo:42|c
sozu.backend.bytes_in,cluster_id=foo,backend_id=foo-0:42|c

在 2.0.0 中，默认 metrics.detail = "cluster"，仅第一个系列被发射。 除非操作员 opt-in 到 metrics.detail = "backend"， 否则 sozu.backend.* 系列无声消失。

操作员影响：如果 metrics.detail 保持默认值， 按 backend_id 分组的仪表板 / 告警规则将在升级时变空白。 这与上面 http.errors 标签变更独立——它影响所有之前携带后端标签的指标 （bytes_in、bytes_out、backend_response_time、 backend_connection_time、每后端 requests）。

操作：如果任何仪表板按 backend_id 分组 sozu.backend.* 系列， 在滚动 2.0.0 之前在配置 TOML 中设置以下内容：

[metrics]
# ... 现有字段 ...
detail = "backend"

运行时 SetMetricDetail TTL 租约动词——通过 sozu top --detail backend --lease-ttl-seconds N 暴露 （默认：TUI 启动时自动应用的 Backend 级别）——也可以在 不重启 worker 的情况下为有界窗口提升级别；对一次性调查有用， 无需承诺永久基数成本。参见 doc/sozu-top.md § 基数。

模式 trie 段正则锚定（CWE-1023 修复）¶

插入到路由 trie 的每个段级正则表达式现在在插入时用 \A...\z 包装。像 cdn[0-9]+ 的模式现在精确匹配 cdn1， 但不匹配 cdn1xxx。

操作员影响：依赖部分段匹配的正则前端（例如 cdn[0-9]+ 规则意外匹配 cdn123xxx）会中断—— 以前匹配的流量不再匹配。

操作：在升级前审计你的正则前端。如果不能预升级审计， 显式扩展模式：cdn[0-9]+.* 以保持 1.1.x 语义。

HAProxy 风格空 val 删除头部语义¶

Header { position, key, val } 条目现在用 HAProxy 对等性处理：

  • position = SET, val = "x" → 将头部设置为 "x"。
  • position = APPEND, val = "x" → 追加值为 "x" 的头部。
  • position = SET, val = "" → 按名称删除头部 （HAProxy del-header 对等性）。

操作员影响：任何将自定义头部设置为空字符串的 1.1.x 配置 （意图"无值，但存在"）现在将从转发请求中删除这些头部。

操作：审计你的 TOML / 运行时 API 状态中的 Header { val = "" } 条目。如果你意图保持头部存在， 设置为仅空格的值 " "——尽管这按 RFC 9110 §5.5 是畸形的， 应审查。

低于 16393 的 buffer_size 在配置加载时拒绝¶

当任何 https_listeners[].alpn_protocols 包含 "h2" 时， 全局 buffer_size 现在在启动时验证是否满足 H2_MIN_BUFFER_SIZE = 16 393（RFC 9113 §6.5.2 + §4.1： 16 384 字节最大 H2 帧载荷 + 9 字节帧头）。

具有 buffer_size = 8192 和任何 H2 监听器的 1.1.x 部署 将拒绝启动 2.0.0，带 ConfigError::BufferSizeTooSmallForH2 { buffer_size, minimum, listeners }。

操作：要么将 buffer_size 提高到 ≥ 16 393， 要么从受影响监听器的 alpn_protocols 中移除 "h2"。 1.1.x 静默死锁行为（其中 buffer_size = 8192 干净启动， 仅在 H2 帧流量下挂起）不再可达。

密码列表常量重命名¶

内部 Rust 常量 DEFAULT_RUSTLS_CIPHER_LIST in command/src/config.rs 重命名为 DEFAULT_CIPHER_LIST。

  • TOML 键不变：在 TOML 中使用 cipher_list = [...] 的操作员不受影响。
  • sozu-command-lib 消费者 按名称导入公共常量的必须更新。

潜在的 DEFAULT_CIPHER_SUITES（OpenSSL 风格名称，rustls 从不匹配）已删除。 P-521 从默认 groups_list 移除（rustls 0.23 不支持它）。

操作：重建引用旧常量的下游 Rust crate。

新 TOML 键（附加；回滚时忽略）¶

2.0.0 引入几个新 TOML 键。它们默认安全值；1.1.x 在回滚时静默忽略它们。

键 默认值 含义
forwarded_for_mode "x-forwarded" 每前端 Forwarded 头部策略（x-forwarded / rfc7239 / both / none）。RFC 7239 支持在后续版本落地。
evict_on_queue_full false 接受队列饱和时驱逐 1% LRU 会话而非拒绝新接受。默认关闭（DDoS 安全）。
max_connections_per_ip 0 限制一个源 IP 对一个集群持有的同时前端连接数。0 = 禁用。
splice_pipe_capacity_bytes None Linux splice(2) 内核管道大小。None 保持内核默认 64 KiB。
basic_auth_max_credential_bytes 4096 最大解码 Authorization: Basic 凭证长度。
command_allowed_uids []（具有 mode-0600 访问权限的任何 UID） 命令 socket 上的可选 Vec<u32> UID 允许列表。
audit_logs_target None 可选专用文本审计日志 sink（PCI-DSS 10.5）。
audit_logs_json_target None 可选专用 JSON 审计日志 sink 用于 SIEM 摄入。

操作员影响：2.0.0 以 1.1.x 等效行为启动（驱逐关闭、每 IP 限制关闭、 X-Real-IP 省略关闭）。显式 opt-in 到新行为。

systemd 单元文件：Type=simple → Type=notify (#228)¶

捆绑的 os-build/systemd/sozu.service 和 sozu@.service 单元从 Type=simple 翻转到 Type=notify + NotifyAccess=main。 主进程现在仅在初始 worker 生成且已保存状态已回放后， 通过 $NOTIFY_SOCKET 向 systemd 发送 READY=1 （参见 command/src/sd_notify.rs）。 STOPPING=1 在优雅关机时触发；热升级 re-exec 路径也发送 MAINPID=<new-pid> 后跟 READY=1。

捆绑单元的操作员影响：无——重新安装 2.0.0 RPM / Arch / Debian 包 会拾取新单元文件。systemctl daemon-reload 后现有 systemctl status sozu 输出获得 active (running) 状态， 仅在主进程真正就绪后翻转；After=sozu.service 对等体（如监控代理） 现在可以依赖它。

自定义单元文件的操作员影响：如果你运送覆盖 Type=simple 的 自己的单元文件，可以翻转到 Type=notify + NotifyAccess=main 以获得就绪门控。2.0.0 二进制也与 Type=simple 向后兼容：当 $NOTIFY_SOCKET 未设置时辅助函数是无操作。

抽象 $NOTIFY_SOCKET（容器、命名空间门控主机）： 以 @ 开头的地址（sd_notify(3) 的 Linux 抽象 socket）被尊重。 command/src/sd_notify.rs::send_abstract 通过 AF_UNIX + 前导 NUL sun_path 路由而非解析为文件系统路径。

_mutation 动词周围的 RELOADING=1 窗口：主进程在每个通过 命令 socket 调度的突变动词的入口处发出 RELOADING=1， 在 LoadState、ReloadConfiguration、 AddCluster / Backend / Certificate / Frontend / Listener、 Remove*、Replace*、Update*、SetHealthCheck、 SetMaxConnectionsPerIp、UpgradeMain、UpgradeWorker、 SoftStop / HardStop 完成时发出 READY=1。 只读动词（Status、List*、Query*、CountRequests、 SubscribeEvents）跳过括约。观察 systemctl show -p ActiveState sozu 的工具可以序列化 对抗重载窗口。热升级路径利用此门控： 旧主进程的出站 STOPPING=1 被抑制，因此它不能竞态 新主进程的 MAINPID= notify（否则会将单元翻转为 inactive 而 sozu 仍在服务流量）。

WatchdogSec= 故意未设置：捆绑单元不声明 WatchdogSec=，且主进程事件循环尚未发射 WATCHDOG=1 周期 ping。常量 STATE_WATCHDOG 为周期定时器后续保留。操作员在自定义单元中添加 WatchdogSec= 将看到 systemd 因缺少 ping 杀死单元—— 不要在周期定时器布线落地前启用它。

TLS 证书链去重 (#1135 / #1148)¶

ACME 客户端（Certbot 默认 fullchain.pem、lego、acme.sh） 在链文件开始处发射叶子证书。在 1.1.x 中解析器 将链存储为 [leaf, leaf, intermediate, root]（双重叶子）， 被浏览器接受但被更严格验证器拒绝（Node.js → UNABLE_TO_VERIFY_LEAF_SIGNATURE）。

在 2.0.0 中解析器去重：每个链条目的 DER 字节与叶子比较， 匹配时丢弃。每个链条目也通过 split_certificate_chain 扇出， 因此携带多个 PEM 块的单字符串（操作员通过运行时 API 路径 将 fullchain.pem 内容连接到单链条目，常见）正确拆分为 每个 CA 一个条目后再解析。

操作员影响：正确链无影响。如果你的链文件已经是 fullchain.pem（叶子优先），线上链缩短一个证书； 客户端看到干净的 [leaf, intermediate, …] 链。 当至少一个重复被丢弃时每个 cert add 触发一次 debug! 日志行：

TLS-RESOLVER >>> dropped 1 duplicate leaf certificate(s) from the supplied chain

这是信息性的，非警告——去重是预期行为。在生产中定位它的 操作员应设置 log_level = "debug" 用于 TLS-RESOLVER 目标 或直接监视线上链长度。

附加 RedirectPolicy 变体：302 + 308 (#1009)¶

RedirectPolicy 枚举在现有 PERMANENT（301）旁获得两个变体：

策略 状态 RFC 跟随时保留方法？
PERMANENT 301 9110 §15.4.2 UA 可能重写 POST → GET
FOUND 302 9110 §15.4.3 UA 可能重写 POST → GET
PERMANENT_REDIRECT 308 9110 §15.4.9 必须保留方法

操作员影响：附加——声明为 redirect = permanent 的现有前端 继续发射 301。仅在需要新语义时使用 redirect = found 或 redirect = permanent_redirect。 两个新指标附带：http.302.redirection 和 http.308.redirection（集群 + 后端标签，镜像现有 http.301.redirection）。

重命名内联模板编译错误计数器¶

内联模板编译失败以前在每状态计数器 http.301.redirect_template.compile_error 下呈现。 现在 302 和 308 模板可以同样失败，每状态形式会留下这些失败 未监控——因此计数器折叠为单个与状态无关键：

之前 (1.1.x) 之后 (2.0.0)
http.301.redirect_template.compile_error http.redirect_template.compile_error

操作员影响：抓取旧键的仪表板或告警需要更新。新键记录在 doc/configure.md 中与新 http.302.redirection 和 http.308.redirection 成功计数器并列。

回滚流程¶

如果在生产中 2.0.0 后出现回归，回滚到 1.1.x：

# 1. 停止 2.0.0 二进制（优雅）
systemctl stop sozu

# 2. 恢复 1.1.x 二进制
install -m 0755 /var/lib/sozu/sozu.1.1.1 /usr/bin/sozu

# 3. 恢复 1.1.x 状态文件
cp /var/lib/sozu/state.1.1.x.backup.json /var/lib/sozu/state.json

已知不可回滚¶

  • 2.0.0 写入的状态文件不能被 1.1.x 加载。 SaveState 是 JSON 序列化的 WorkerRequest，带来自当前 proto schema 的 serde 生成名称。 没有已证明的旧 serde 生成结构的向前兼容契约。任何 2.0.0 升级后的状态变更（sozu cluster add、sozu certificate add 等）不会 幸存二进制回滚。 手动重放升级后变更到预升级状态文件备份。
  • 审计日志文件由 2.0.0 的 JSON sink 写入不会在 1.1.x 消费者中解析（新 schema 带审计事件 v2 字段）。
  • 访问日志带有新 tls_version / tls_cipher / tls_sni / tls_alpn / xff_chain 字段不会在 1.1.x 消费者中解析。
  • 模式 trie 正则锚定是永久代码级行为变更。 依赖部分匹配的操作员 已为 2.0.0 调整他们的正则；回滚到 1.1.x 恢复部分匹配但操作员已扩展模式—— 净中性。
  • TOML 不匹配危险：如果你在升级时向监听器添加 H2 ALPN WITH buffer_size < 16393，1.1.x 不会拒绝配置（只是第一次 H2 帧挂起）。 回滚时还原 TOML 变更。
  • 新 TOML 键（forwarded_for_mode、evict_on_queue_full、 max_connections_per_ip、splice_pipe_capacity_bytes、 basic_auth_max_credential_bytes、command_allowed_uids、 audit_logs_target、audit_logs_json_target）被 1.1.x 静默忽略—— 回滚时从 TOML 移除它们以便干净解析。

2.0.0 后支持的版本¶

按 SECURITY.md：

  • 2.0.x —— 当前；接收安全修复。
  • 1.1.x —— 在 2.0.0 发布时 end-of-life。 不再安全回port。 操作员预期升级到 2.x。
  • 1.0.x 及更早——不受支持。
